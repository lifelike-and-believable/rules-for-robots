# rules-for-robots

Rules, best practices, and agent definitions that steer Claude Code toward high-quality software, websites, web apps, and Unreal Engine plugins. The plan is in `PLAN.md`; the evidence behind it is in `docs/research/`. Read `docs/handoff.md` at the start of a session for the current state and the maintainer's standing direction, and update it before the session ends.

## Commands

- Verify (run before reporting work as done, and include its output): `npm run verify`
- Regenerate template repos after changing `rules/` or `templates/`: `npm run build`

## Layout

- `rules/`: source of truth, one rule per file. Format: `docs/rule-format.md`.
- `template-repos/`: generated entirely by `npm run build` from `rules/`, `templates/agents-md/`, and `templates/repo-files/` (shared `common/` plus one folder per profile). Edit the sources, never these files.
- `plugins/core/`: the `rfr-core` plugin. `skills/install-rules/payload/` is generated by the build. Bump `version` in its `plugin.json` whenever its contents change, or installed copies will not update.
- `plugins/process/`: the `rfr-process` plugin (`docs/specs/project-process.md`). `scripts/lib/process.mjs` is generated by the build from `checks/lib/process.mjs`. Bump its `version` the same way.
- `plugins/feedback/`: the optional `rfr-feedback` plugin (`docs/specs/feedback.md`), which files feedback issues on this repository. No other plugin depends on it. Bump its `version` the same way.
- `.claude/skills/triage-feedback/`: the skill a session on this repository uses to triage feedback issues; `.github/ISSUE_TEMPLATE/feedback.yml` and `.github/workflows/feedback-intake.yml` handle intake.
- `.claude-plugin/marketplace.json`: makes this repo a plugin marketplace.
- `checks/unreal/tier1.mjs`: engine-free Unreal checks used by the `unreal-plugin` pack's CI. `examples/unreal/RfrSample/`: minimal plugin those checks and the Tier 2 workflow run against.
- `practices/`: longer guides that rules link to.
- `.github/workflows/rfr-guards.yml`, `rfr-unreal-tier1.yml`, `rfr-process.yml`, `rfr-tutorials-preview.yml`: reusable workflows that adopting repos call.
- `plugins/process/vale/RFR/`: the Vale style the `docs-lint` job uses; `checks/ci/install-vale.mjs` pins Vale by SHA-256 into `.cache/` (gitignored). `checks/ci/`: scripts they run.
- `checks/`: rule lint and shared parsing. `build/`: template repo renderer and profiles. `test/`: tests for both, and for rfr-core and rfr-process. The domain plugins (rfr-web, rfr-unreal, rfr-android, rfr-feedback) keep their tests in `plugins/<name>/test/`; in CI, `checks/ci/verify-ci.mjs` runs those only when something they depend on changes, and runs no tests for a documents-only pull request.
- `docs/research/`: Phase 0 findings, recommendations, notes, and experiments. Treat as a record; correct errors, but do not rewrite history.

## Writing rules and docs

- Follow `docs/rule-format.md` for every rule. The lint enforces most of it.
- A MUST rule needs a hook or CI check, and evidence from an authoritative source or our own eval.
- Canadian English. Plain sentences; no emphatic capitals, few em dashes, no "it's not X, it's Y" constructions.

## Working on this repo

- Change existing test files with the Edit tool (or MultiEdit), never through shell commands or scripts; rfr-core refuses a shell write to one.
- One plan slice per branch and pull request, named `phase-<n>/<slice>`.
- Name a new test file by the behaviour it covers (`process-stage-order.test.mjs`), not by the pilot round that found it. Existing files keep their names.
- Update `PLAN.md` when a slice answers an open question or changes a decision. When a slice completes a phase or milestone item, add its pull request to that item's `Pull requests:` line or column in the same pull request, once the number is known (`npm run check:plan` fails on completed work with no pull request).
- Name the pull request in the changelog entry for each release, and end each plugin entry with an "Adopters:" line: "nothing to do", or what an adopting project changes.
