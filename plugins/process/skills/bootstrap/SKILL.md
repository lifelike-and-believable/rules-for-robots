# Bootstrap an existing project

An existing project has code and users but no process artifacts. This skill drafts the product-level artifacts from what already exists, so the approver reviews instead of writing from nothing. Everything it writes is a `draft`; only the approver approves, by reviewing or merging the pull request. Templates are in `${CLAUDE_SKILL_DIR}/../../templates/`, and how to write each artifact is in `${CLAUDE_SKILL_DIR}/../../GUIDE.md`.

1. **Check the setup.** `docs/product/process.yml` must exist; if it does not, run `/rfr-process:setup` first. If `docs/product/concept.md` already has content beyond the template, stop and ask before replacing it.
2. **Gather evidence.** Read the README, existing documentation, the changelog, open and recently closed issues (`gh issue list --state all --limit 100` if `gh` is available, or the GitHub tools you have), the code's public surface (routes and pages for a web app; the `.uplugin`, public headers, Blueprint-exposed functions, and settings classes for an Unreal plugin), and the running product where you can reach it. Find where the live content comes from (files in the repository, a CMS, a database, an outside service) and check it against the code: a repository can hold a content folder or schema the live site no longer reads. Use a subagent for broad reading and keep only its conclusions. Note where each fact comes from. When sources disagree, the code and the running product outrank planning documents, which are often out of date: use documents for intent, and list each contradiction as an open question. Leave existing planning documents where they are and cite them as evidence.
2a. **Ask once.** Put every question the concept and requirements need in one message to the user, each with the answer the evidence suggests. Draft without waiting for questions that stay unanswered: write the proposed answer in the artifact and mark it `[assumed]`.
2b. **Ask how the product will be tried.** In the same message, ask how the product will be tried: the local command, whether pull requests get previews, and the deployed address, each with an answer proposed from what the repository shows (a `try` or `start` script, a host's preview configuration, the address in the README). By profile: `web-app` and `static-site` propose a `try` script and the host's previews; `unreal-plugin` proposes the sample project in the editor and no `try:` block; `general` proposes the built tool, or none. Write the `try:` block in `docs/product/process.yml` from the answers. The first slice of a product with a user interface builds the `try` command, and the first slice with accounts builds tutorial sign-in, so a command that does not exist yet is noted for that slice.
3. **Draft the concept** in `docs/product/concept.md`: problem, audience, vision, non-goals, as the project's own materials describe them. Mark anything inferred rather than stated with "(inferred from ...)".
4. **Draft requirements** in `docs/product/requirements/<area>.md`, one file per area of capability the project already has. Each requirement gets an ID heading (`## REQ-<area>-1: ...`) and states what users can see and do, written so it can be tested. Do not name the tools or services that implement it today (a CMS, a payment provider, a hosting platform): record those in `docs/product/notes.md`, which is not a process artifact, so a change of provider is not a change to an approved requirement. Do not infer non-goals from features the project happens not to have; ask about them as open questions instead. List open questions at the end of each file rather than guessing.
5. **Draft personas** in `docs/product/personas/` from the evidence: who files issues, who the documentation addresses, who the profile's starters in `templates/profiles/<profile>/personas/` describe. A starter can be split into several personas or folded into one; say which in the persona's evidence note. Prefer two or three well-evidenced personas to many thin ones. Each persona says what evidence it rests on.
6. **Link them.** Link to sections, not whole artifacts, so a later edit to one section of the concept does not make everything stale: requirements link to `concept#vision`, and personas to `concept#audience`. Leave hashes empty; they are recorded when each artifact is approved (`node .rfr/checks/process-relink.mjs <id>`).
7. **Set the adoption window.** Add `adoption-until: <today plus the window from $ARGUMENTS, default 90 days>` to `process.yml`, so existing work without links produces warnings until then.
7a. **Write the start page.** The start page, `docs/user/README.md`, is written with the product brief from `templates/artifacts/user-docs-start.md`, once the areas are known from the design. It lists the areas in the order a user meets them and gives each persona a place to start.
8. **Check.** Run `node .rfr/checks/process-trace.mjs` and show the result. Run the cross-area consistency pass (requirements across areas and against the concept) and the `persona-walkthrough` agent on the requirements, fix what they find, and build the review packet with `node .rfr/checks/process-packet.mjs . --base <default branch> --walkthrough <report.md>` for the top of the pull request description: the drafts go to the approver as one product brief.
9. **List the defects found.** Gathering evidence often turns up bugs: broken links, inaccessible controls, behaviour that contradicts the project's own documents. They are not requirements. List them in the summary, each with where it shows and the requirement it breaks, so they can become fix issues once the requirements are approved.
10. **Stop.** Summarize what was drafted, the open questions, the defects found, and the evidence behind each persona. The approver reviews these before any epics or stories are written. Commit only if the user asks, or if the task you were given is to open a pull request.
11. **When the approver says the drafts are ready**, set each approved artifact to `status: approved`, record its hashes (`node .rfr/checks/process-relink.mjs <id> ...`, upstream first: concept, then requirements and personas), run the process check, and push to the same pull request. Merging (solo) or approving (team) that commit is the approval; merging while the artifacts say `draft` approves nothing. Do not merge it yourself unless the approver explicitly tells you to, and if they do, comment on the pull request quoting their instruction.
