# Set up the process

The process is described in the rules-for-robots spec `docs/specs/project-process.md` and in `${CLAUDE_SKILL_DIR}/../../README.md`. Templates are in `${CLAUDE_SKILL_DIR}/../../templates/`.

1. **Choose the profile and mode.** Take them from `$ARGUMENTS`. Otherwise infer the profile from the repository (a `.uplugin` file: `unreal-plugin`; Astro: `static-site`; Next.js or another web app: `web-app`) and ask the user to confirm it, and ask whether approvals are `solo` (one person approves everything by merging) or `team` (approving reviews, with approvers per stage). Ask for the approvers' GitHub logins.
2. **Check for a repository.** If the folder is not a git repository (`git rev-parse --is-inside-work-tree` fails), stop and tell the user: approval is a merged pull request, so the process needs a repository and a remote. Offer the commands (`git init -b main`, then adding the remote), and run them only if the user agrees. Say that the first commit of a new repository, with the configuration and any drafts, goes straight to the default branch (the approvals job skips a commit with no parent); approvals start with the first pull request after it. In a repository that already has commits, everything goes through a pull request.
3. **Check what exists.** If `docs/product/process.yml` already exists, stop and show it; do not overwrite. If the repository already has code and documentation but no process artifacts, tell the user about `/rfr-process:bootstrap`, which drafts the first artifacts from what exists.
4. **Write the configuration.** Copy `templates/process.yml` to `docs/product/process.yml` and fill in `mode` and `default`. For a team, add a `stages` entry only where the user names a different approver.
5. **Add the workflow.** Copy `templates/workflows/rfr-process.yml` to `.github/workflows/rfr-process.yml`, beside any CI the repository already has. Change `branches: [main]` if the default branch has another name. For `web-app` and `static-site`, also offer two optional additions and add them only if the user agrees: Stryker (copy `templates/profiles/<profile>/stryker.config.mjs` to the project root, give the user the `npm install --save-dev --save-exact` command in its header, and add `mutation: true` under `with:` in the caller), and, when the project has preview deployments, `templates/workflows/rfr-tutorials-preview.yml`. The template follows rules-for-robots `main`, which suits a pilot; for a project that needs stable CI, pin both the `uses:` line and the `rules-ref` input to a release tag or commit (see the README).
6. **Add starters.** Copy `templates/artifacts/concept.md` to `docs/product/concept.md`. For a new project, also copy the profile's persona starters from `templates/profiles/<profile>/personas/` to `docs/product/personas/`, and tell the user they are starters to replace with what they know about their real users. For an existing project that will run `/rfr-process:bootstrap` next, do not copy them: bootstrap drafts personas from evidence and uses the starters only as a checklist. Copy nothing else yet; the other templates are used when each artifact is written.
7. **Record the agent rules in the project.** Add a short "Development process" section to the project's `AGENTS.md` (create it if there is none; `CLAUDE.md` can import it with `@AGENTS.md`): the project uses rfr-process (link the rules-for-robots README); agents do not merge pull requests that touch `docs/product/`, `docs/design/`, `docs/user/`, or `docs/tutorials/` unless the approver explicitly says to, and then comment on the pull request quoting the instruction; artifacts are approved by a pull request that sets `status: approved` and records hashes. This keeps the rules in force when an agent works without the plugin installed, where the merge guard hook does not run.
8. **Team mode only.** Run `node .rfr/checks/process-codeowners.mjs` from a checkout of rules-for-robots at `.rfr` (or give the user the command), and list the branch protection settings to turn on: require the `process / approvals` and `process / tier` checks.
9. **Labels.** The workflow's tier job creates the labels `tier:trivial`, `tier:fix`, `tier:story`, and `tier:epic` on its first run, so nothing is needed here. The pull request that adds `process.yml` needs no tier label. If the user wants the labels sooner, give them the `gh label create` commands, or the web route (the repository's Issues, then Labels); do not run anything without asking.
10. **Check.** Run `node .rfr/checks/process-trace.mjs` if `.rfr` is available, and show the result. Drafts with no links are expected at this point.
11. **Stop.** List the files written and the next step: write the concept, then requirements and personas, each approved before the next builds on it. Point the user to `${CLAUDE_SKILL_DIR}/../../GUIDE.md` for how to write each artifact and what each review checks. Commit only if the user asks, or if the task you were given is to open a pull request.
