# Set up the process

The process is described in the rules-for-robots spec `docs/specs/project-process.md` and in `${CLAUDE_SKILL_DIR}/../../README.md`. Templates are in `${CLAUDE_SKILL_DIR}/../../templates/`.

1. **Choose the profile and mode.** Take them from `$ARGUMENTS`. Otherwise infer the profile from the repository (a `.uplugin` file: `unreal-plugin`; Astro: `static-site`; Next.js or another web app: `web-app`; anything else, such as a command-line tool, a service, or a desktop, mobile, or TV app: `general`, whose tutorials are `runner: manual`) and ask the user to confirm it. Use `general` rather than borrowing another profile's personas and templates for a project they do not describe. When `general` is the choice because nothing fits, and the project would gain from its own profile, offer to suggest one with `/rfr-feedback:report-feedback` (area `profiles`): what kind of project it is and the files that identify it (an `AndroidManifest.xml`, a `pyproject.toml` with a CLI entry point); what it had to borrow or do without (another profile's templates, a manual tutorial pass, a guard that asks too often or not at all, missing allow rules); and why a profile would help, with the concrete cost seen so far. If there is nothing to infer from (a repository that holds only documents so far), ask which profile fits; do not guess. Then ask whether approvals are `solo` (one person approves everything by merging) or `team` (approving reviews, with approvers per stage), and for the approvers' GitHub logins.

   **Several sub-projects** (`mixed`): when the repository holds, or will hold, more than one kind of project (a web app and an Unreal plugin, say), there is one set of artifacts and one `process.yml` for the whole repository, and each sub-project has its own profile. Ask for each sub-project's folder (or planned folder) and profile, and note any that fits no profile (a Claude Code plugin, for example): use the closest profile's templates for it, and say which. The profile only decides which starters and templates setup offers; the checks do not read it.
2. **Check for a repository.** If the folder is not a git repository (`git rev-parse --is-inside-work-tree` fails), stop and tell the user: approval is a merged pull request, so the process needs a repository and a remote. Offer the commands (`git init -b main`, then adding the remote), and run them only if the user agrees. Say that the first commit of a new repository, with the configuration and any drafts, goes straight to the default branch (the approvals job skips a commit with no parent); approvals start with the first pull request after it. In a repository that already has commits, everything goes through a pull request.
3. **Check what exists.** If `docs/product/process.yml` already exists, stop and show it; do not overwrite. If the repository already has code and documentation but no process artifacts, tell the user about `/rfr-process:bootstrap`, which drafts the first artifacts from what exists. Then list the files steps 4 to 7 will write and ask the user once for the change that covers them (rfr-core WA-009): accept-edits mode for the repository's folder, and `/add-dir` first if the repository is outside the session's folders, so each file does not prompt on its own.
4. **Write the configuration.** Copy `templates/process.yml` to `docs/product/process.yml` and fill in `mode` and `default`. For a team, add a `stages` entry only where the user names a different approver.
5. **Add the workflow.** Copy `templates/workflows/rfr-process.yml` to `.github/workflows/rfr-process.yml`, beside any CI the repository already has. Change `branches: [main]` if the default branch has another name. For `web-app` and `static-site` (in a mixed repository, for each such sub-project, with the Stryker configuration in that sub-project's folder), also offer two optional additions and add them only if the user agrees: Stryker (copy `templates/profiles/<profile>/stryker.config.mjs` to the project root, give the user the `npm install --save-dev --save-exact` command in its header, and add `mutation: true` under `with:` in the caller), and, when the project has preview deployments, `templates/workflows/rfr-tutorials-preview.yml`. The template follows rules-for-robots `main`, which suits a pilot; for a project that needs stable CI, pin both the `uses:` line and the `rules-ref` input to a release tag or commit (see the README).
6. **Add starters.** Never replace a file that already exists: if `docs/product/concept.md` or a persona file is already there, leave it and say so. Otherwise copy `templates/artifacts/concept.md` to `docs/product/concept.md`. For a new project, also copy the profile's persona starters from `templates/profiles/<profile>/personas/` to `docs/product/personas/` (for a mixed repository, from each profile used, keeping one copy of starters that describe the same kind of user), and tell the user they are starters to replace with what they know about their real users. For an existing project that will run `/rfr-process:bootstrap` next, do not copy them: bootstrap drafts personas from evidence and uses the starters only as a checklist. Copy nothing else yet; the other templates are used when each artifact is written.
7. **Record the agent rules in the project.** Add a short "Development process" section to the project's `AGENTS.md` (create it if there is none; `CLAUDE.md` can import it with `@AGENTS.md`): the project uses rfr-process (link the rules-for-robots README); agents do not merge pull requests that touch `docs/product/`, `docs/design/`, `docs/user/`, or `docs/tutorials/` unless the approver explicitly says to, and then comment on the pull request quoting the instruction; artifacts are approved by a pull request that sets `status: approved` and records hashes. This keeps the rules in force when an agent works without the plugin installed, where the merge guard hook does not run. For a mixed repository, add a table of sub-project folders and their profiles, and say that user documentation and tutorials for each sub-project start from that profile's templates (`templates/profiles/<profile>/` in the plugin).
8. **Team mode only.** Run `node .rfr/checks/process-codeowners.mjs` from a checkout of rules-for-robots at `.rfr` (or give the user the command), and list the branch protection settings to turn on: require the `process / approvals` and `process / tier` checks.
9. **Auto-merge (optional).** Tell the user that turning on "Allow auto-merge" in the repository settings (Settings, General) lets an agent act on "merge when green" by enabling auto-merge on that pull request, rather than waiting for CI itself. Do not change the setting yourself.
10. **Labels.** The workflow's tier job creates the labels `tier:trivial`, `tier:fix`, `tier:story`, and `tier:epic` on its first run, so nothing is needed here. The tier job infers each pull request's tier from its paths, so a label is needed only to raise it; the pull request that adds `process.yml` needs none. If the user wants the labels sooner, give them the `gh label create` commands, or the web route (the repository's Issues, then Labels); do not run anything without asking.
11. **Check.** Run `node .rfr/checks/process-trace.mjs` if `.rfr` is available, and show the result. Drafts with no links are expected at this point.
12. **Stop.** List the files written and the next step: a product brief (concept, requirements, personas, and epics in one pull request, after one batched interview, with the review packet from `checks/process-packet.mjs` at the top), then a feature packet per story. Point the user to `${CLAUDE_SKILL_DIR}/../../GUIDE.md` for how to write each artifact and what each review checks. Commit only if the user asks, or if the task you were given is to open a pull request.
