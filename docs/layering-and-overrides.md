# Layering and overrides

Claude Code concatenates every instruction file it loads and, when two conflict, may follow either. So rules-for-robots never layers by adding a contradicting instruction. Every layer adds, removes, or replaces whole rule files.

## Layers

| Layer | Where | How it changes rules |
|---|---|---|
| Core and packs | `.claude/rules/core/`, `.claude/rules/packs/<pack>/` (installed from this repo) | Choose packs at install time |
| Organization | Organization template repo or installer skill; managed settings | Adds files with its own ID prefix; tightens SHOULD to MUST by adding hooks or CI checks |
| Team and project | The project's `.claude/rules/` and CI | Adds files; waives rules by replacing files; excludes files with `claudeMdExcludes` |
| Personal | `CLAUDE.local.md`, user settings | Preferences that do not contradict project rules |

## Waiving a rule

Replace the rule's file with a waiver of the same name: frontmatter only, no body, so nothing reaches the model.

```yaml
---
id: TEST-001
waiver: true
reason: Snapshot tests here are regenerated by a reviewed script.
approved-by: <name>
date: 2026-10-05
---
```

Waiving a MUST rule should also be recorded in an ADR (`/rfr-core:write-adr`), and its hook or CI check adjusted to match. `node checks/lint-rules.mjs .claude/rules --adopting-repo --no-practice-links` validates rule, waiver, and project rule files in an adopting repo.

## Adding rules

Follow [rule-format.md](rule-format.md) with your own ID prefix, so IDs never collide with this repo's. Put project rules in `.claude/rules/project/` with `scope: project`; the lint's `--adopting-repo` mode accepts any prefix there that rules-for-robots does not use. `/rfr-core:install-rules` does not touch `project/`. Keep always-on text (`AGENTS.md` plus rules without `paths`) under 200 lines.

## Updating

Re-run `/rfr-core:install-rules`. It keeps waivers, skips identical files, and asks before replacing files you changed.
