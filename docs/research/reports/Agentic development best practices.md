# Fewer rules and harder gates steer 5.5-class agents

For Opus 5.5 and Sonnet 5.5-class coding agents, the strongest current evidence favours a short, calm, explicitly scoped instruction layer. That layer should hold only project decisions the model cannot infer. Deterministic hooks, linters and CI enforce anything that must always hold, and each rule is kept only if a with-and-without evaluation shows that it changes behaviour. Anthropic's current prompting guidance says these models follow instructions literally, over-trigger on emphatic wording, and (on Opus 5 and 5.5) already verify their own work. Instructions written for older models ("CRITICAL", "think step by step", "always double-check", "show your reasoning") now waste tokens, cause over-verification, or trigger refusals. Independent 2026 studies find that repository context files rarely improve task success, add about 20% to cost, and lose adherence as sessions grow longer. The most common serious agent failures are editing tests so they pass, scope creep, destructive git operations and invented APIs. Prompts reduce these failures substantially when they give the agent an explicit "stop and report" option, but residual rates of roughly 10% remain, so mechanical guards are still needed. For this project, the most consequential finding is a packaging constraint: a Claude Code plugin cannot ship `CLAUDE.md` or `.claude/rules/`, so always-on and path-scoped rules have to reach adopters through the template repo or an installer skill. For Unreal plugins, the installed engine headers and compiler output are the only trustworthy API reference, and the editor's exit code after automation tests cannot be trusted. Many quantitative findings came from abstracts or secondary summaries because the research sandbox blocked arXiv, Epic, Next.js, Vercel and several practitioner sites. Those findings are flagged throughout and should be verified before they support any MUST-level rule.

## Calm, scoped, reasoned instructions now beat emphatic ones

### What Anthropic says about writing for current models

Anthropic's current prompting guide asks for clear, direct and specific instructions, a reason for each constraint, positive phrasing, examples, and XML or Markdown structure. It describes Claude as "a brilliant but new employee who lacks context on your norms" ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)) [Official]. On rationale, the guide replaces "NEVER use ellipses" with a sentence explaining that a text-to-speech engine cannot pronounce them, and says **"Claude is smart enough to generalize from the explanation"** (same source) [Official]. The Fable 5 page repeats the point: the model "tends to perform better when it understands the intent behind a request" ([Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)) [Official]. On emphasis, the guide says that from Opus 4.5 and 4.6 onward the models are "more responsive to the system prompt", and that prompts written to fix under-triggering "may now overtrigger". **Its fix is to replace "CRITICAL: You MUST use this tool when..." with "Use this tool when..."** ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)) [Official]. Claude Code's own guide allows one exception: if Claude keeps skipping one instruction, add "IMPORTANT" to that line alone, because "if you emphasize many lines, none of them stands out" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)) [Official].

Literal reading is the main behavioural change. Opus 4.8 "does not silently generalize an instruction from one item to another", so scope must be stated ("apply this to every section, not just the first one"). The Sonnet 5 entry lists literal instruction following as a change from Sonnet 4.6 ([Prompting Claude Opus 4.8](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-4-8)) [Official]. This also applies to filter wording. **Review prompts that say "only report high-severity issues" or "don't nitpick" make Opus 4.8 and Opus 5 find bugs and then leave them out of the report.** Anthropic's advice is to state the bar concretely, or to "ask it to report everything and filter in a separate pass" ([Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)) [Official]. Generic negative instructions run into the models' default styles. On Opus 5.5, "avoid a generic AI look" "mostly swaps one default for another", while naming specific patterns to avoid works ([Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)) [Official]. Positive framing is a preference, not a ban: Anthropic's own sample prompts still contain short, concrete "don't" lists [Inference].

At the most capable tier, brevity is enough. On Fable 5, "a short brevity instruction is as effective as listing each pattern", and **"skills developed for prior models are often too prescriptive... and can degrade output quality"** ([Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)) [Official]. The context-engineering post says prompts should be pitched at the right level of abstraction. Hard-coded brittle logic and vague high-level guidance both fail; the target is "the minimal set of information that fully outlines your expected behavior", with "diverse, canonical examples" in place of edge-case lists ([Effective context engineering, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)) [Official].

### Instructions written for earlier models that now backfire

Each model generation follows instructions more precisely and is more proactive by default, so instructions that once pushed older models now overshoot. Most of the migration advice is to delete instructions rather than add them.

| Pattern in existing rules | Effect on current models | Scope | Source |
|---|---|---|---|
| "CRITICAL: you MUST use X", "If in doubt, use X", "Default to X" | Over-triggering of tools and skills | Opus 4.5 and later | [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) [Official] |
| "Include a final verification step", "use a subagent to verify", "double-check" | **Over-verification; remove rather than rewrite** | Opus 5 (Opus 5.5 inherits Opus 5 patterns) | [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5) [Official] |
| "Think carefully before answering" | Unneeded; effort is the control, and removing it made replies start sooner with no clear quality loss | Opus 5.5 | [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5) [Official] |
| "Write out your reasoning", fixed-format thinking | **May be declined with a `reasoning_extraction` refusal** | Opus 5, Fable 5, Opus 5.5, Sonnet 5.5 | [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5) [Official] |
| "Do not think / do not reason" | Increases thinking-tag leakage | Opus 5, Sonnet 5.5 | [Prompting Claude Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5) [Official] |
| "After every 3 tool calls, summarize progress" | Unneeded scaffolding | Opus 4.8 and later | [Prompting Claude Opus 4.8](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-4-8) [Official] |
| "Only use tools when strictly necessary", "hold all findings for the final response" | Remove | Sonnet 5.5 | [Prompting Claude Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5) [Official] |
| Long "avoid excessive markdown" blocks | Can suppress structure the content needs | Fable 5.1 | [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) [Official] |

The verification row reverses between models. Opus 5 should have verification instructions removed. **Sonnet 5.5 at `low` or `medium` effort may check in before finishing or skip verification, so a concrete "run a real check" paragraph is recommended for it** ([Prompting Claude Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)) [Official]. Sonnet 5.5 also "tends to add tests, documentation, and small supporting files" at every effort level. At xhigh and max effort it launches its own reviewer subagents, and a scope paragraph that stopped this **"cut session cost by about a third, with no change in quality"** (same source) [Official]. Opus 5.5 runs adaptive thinking at default `medium` effort, which "matches or exceeds Claude Opus 5 at `high`". Its new failure mode is ending an unattended turn with a progress report, and it "is responsive to instructions that name the specific kinds of early stop you want it to avoid" ([Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)) [Official]. The general guide states the meta-rule: where a technique names a model, "treat it as measured on that model and re-check it against your own evals before applying it to another" ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)) [Official]. A rule set that spans both models should therefore control depth and thoroughness through effort settings and concrete project commands, and should avoid generic booster lines [Inference].

### Length: short files are favoured, but the evidence is mixed

Claude Code's documentation sets a working limit: **"target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence."** Imports organize a file "but don't reduce its context cost" ([Claude Code memory](https://code.claude.com/docs/en/memory)) [Official]. The pruning test is "Would removing this cause Claude to make mistakes? If not, cut it." The include/exclude table keeps commands Claude cannot guess, non-default style rules, test instructions, repo etiquette, architectural decisions, environment quirks and gotchas. It excludes anything inferable from code, standard conventions, API docs, tutorials, file-by-file descriptions and "write clean code" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)) [Official]. The research partly supports this:

| Study | Setup | Finding | Tag |
|---|---|---|---|
| IFScale, [arXiv 2507.11538](https://arxiv.org/abs/2507.11538) (Jul 2025) | 10 to 500 keyword-inclusion instructions, 20 models | Best frontier models reached only 68% at 500 instructions; omission was the main failure | [Research; secondary only] |
| Evaluating AGENTS.md, [arXiv 2602.11988](https://arxiv.org/abs/2602.11988) (Feb 2026) | Claude Code (Sonnet 4.5), Codex, Qwen Code | **Context files "do not generally improve task success rates" and raise cost "by over 20%"**; instructions are followed; repo overviews do not help; developer-written files beat LLM-generated ones | [Research; secondary only] ([InfoQ](https://www.infoq.com/news/2026/03/agents-context-file-value-review/)) |
| Factorial adherence study, [arXiv 2605.10039](https://arxiv.org/abs/2605.10039) (May 2026) | 1,650 Claude Code sessions, Sonnet 4.6 and Opus 4.6/4.7, one simple target rule | File size, position, hierarchy and a conflicting rule had **no detectable effect**; **each additional generated function lowered odds of compliance by about 5.6% (OR 0.944)** | [Research; secondary only] |
| Two-agent ablation, [arXiv 2607.27250](https://arxiv.org/abs/2607.27250) (Jul 2026) | Claude Code and Codex, 17 real tasks, 288 runs | Context strategy did not move correctness (bounded to 10 to 15 points); failures were implementation skill, not missing repo knowledge | [Research; secondary only] |
| AGENTS.md efficiency, [arXiv 2601.20404](https://arxiv.org/abs/2601.20404) (Jan 2026) | Codex, 10 repos, 124 PRs | Median runtime fell 28.64% and output tokens 16.58% with AGENTS.md | [Research; secondary only] |
| Configuration smells, [arXiv 2606.15828](https://arxiv.org/abs/2606.15828) (Jun 2026) | 100 popular AGENTS.md/CLAUDE.md files | 91% had a smell: **lint leakage 62%**, bloat 42%, skill leakage 35%, conflicts 28%, stale `/init` output 24% | [Research; secondary only] ([InfoWorld](https://www.infoworld.com/article/4187057/ai-coding-agents-may-be-getting-bad-instructions-from-smelly-config-files.html)) |

No study tested instruction-count scaling on Opus or Sonnet 5.5. The popular "150 to 200 instructions" figure from HumanLayer ([Writing a good CLAUDE.md](https://www.humanlayer.dev/blog/writing-a-good-claude-md)) [Single source; secondary only] appears to be extrapolated from IFScale-style results and should not be cited as a property of current models. The defensible reading is this: always-loaded text costs tokens every session and rarely raises success rates on its own. **Within-session drift matters more than file layout.** The content that justifies its cost is non-standard, non-inferable requirements, commands and named failure modes. Mechanical rules belong in tooling [Inference].

### Rationale and RFC 2119 keywords

Anthropic endorses giving a reason for each instruction, but **no controlled study of rationale versus no rationale on Claude 4.x or 5.x was found**, and **no empirical study of RFC 2119 keywords and LLM adherence was found**. The available evidence on MUST-style wording points the other way: emphatic language over-triggers ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)) [Official]. Anthropic's skill guide treats stronger wording ("MUST filter" instead of "always filter") as a targeted fix for a rule that has been observed being missed. It also says wording strength should match how strict the requirement really is, with exact commands for fragile operations and heuristics for open-ended ones ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)) [Official]. AWS's Agent SOPs use MUST/SHOULD/MAY and were reportedly "widely adopted inside Amazon", which is adoption evidence, not adherence evidence ([InfoWorld](https://www.infoworld.com/article/4095173/aws-open-sources-agent-sops-to-simplify-ai-agent-development.html)) [Single source]. Claude Code is explicit that "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)) [Official]. Taken together, a rule's level is useful information for humans and CI, and the guarantee for a MUST should come from tooling rather than capital letters [Inference].

## Claude Code offers many mechanisms, and plugins cannot ship rules

### Loading and precedence

`CLAUDE.md` files from the managed, user, project and local scopes are **concatenated, not overridden**. When instructions conflict, "Claude may pick one arbitrarily", and user-level and project rules have the same standing: "Neither set overrides the other" ([Claude Code memory](https://code.claude.com/docs/en/memory)) [Official]. The content arrives **as a user message after the system prompt**, not as part of it. For system-prompt-level instructions the docs point to `--append-system-prompt` (same source) [Official]. `@imports` resolve up to four hops, block-level HTML comments are stripped before injection, and `CLAUDE.local.md` is still supported. `claudeMdExcludes` skips other teams' files in monorepos. Since **v2.1.277 (18 September 2026)** Claude Code reads `AGENTS.md` natively, but only when no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` exists, so the portable pattern is a `CLAUDE.md` that contains `@AGENTS.md` (same source; [Changelog](https://code.claude.com/docs/en/changelog)) [Official]. Auto memory loads the first 200 lines or 25 KB of `MEMORY.md` each session and can be turned off with `autoMemoryEnabled: false` ([Claude Code memory](https://code.claude.com/docs/en/memory)) [Official]. `/doctor prompt-audit` (v2.1.283) flags stale paths, contradictions and "instructions written for older models" across CLAUDE.md, rules, skills, agents and output styles (same source) [Official].

**Path-scoped rules** in `.claude/rules/**/*.md` load at launch when they have no frontmatter. With a `paths:` glob list they load lazily, when Claude uses Read, Write or Edit on a matching file. Before **v2.1.288 (2 October 2026)** only Read triggered them. **`paths` is the only frontmatter field Claude Code reads, any other field "is ignored without an error", and invalid YAML makes the rule load unconditionally** ([Claude Code memory](https://code.claude.com/docs/en/memory); [Changelog](https://code.claude.com/docs/en/changelog)) [Official]. Rules are not triggered by Bash or grep, so a rule for `*.tsx` will not load if the agent only greps those files [Inference from the documented trigger]. An `InstructionsLoaded` hook reports which rules loaded and why (`session_start`, `path_glob_match` and so on), which makes rule loading auditable ([Hooks](https://code.claude.com/docs/en/hooks)) [Official].

### Skills, subagents, hooks, plugins and settings

**Skills** keep only their name and description in context until invoked, and custom slash commands have been merged into them. The skill listing is capped at 1% of the context window, and the least-used descriptions are dropped first when it overflows. Once invoked, a skill's body stays in the conversation, and after compaction **only its first 5,000 tokens are re-attached**, so the important instructions belong at the top. `disable-model-invocation: true` hides a skill from automatic use, and `context: fork` runs it in a fresh subagent, which "only makes sense for skills with explicit instructions". Only six frontmatter keys (`name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`) are portable to claude.ai and the Skills API, where other keys are a hard error ([Skills](https://code.claude.com/docs/en/skills)) [Official]. `claude plugin eval` (v2.1.269) measures how often skills trigger and subagents are delegated to, with and without the plugin ([Changelog](https://code.claude.com/docs/en/changelog)) [Official].

**Subagents** take their system prompt from the body of the markdown file. They see the CLAUDE.md hierarchy and git status but not the conversation, the main Claude Code system prompt or the output style. Their frontmatter can set `tools`, `model`, `effort`, `skills`, `isolation: worktree`, `omitClaudeMd` and more. Nesting defaults to three levels and concurrency to 20, and combined descriptions above 15,000 tokens trigger a warning. **Plugin-shipped agents ignore `permissionMode`, `hooks` and `mcpServers`** ([Sub-agents](https://code.claude.com/docs/en/sub-agents); [Plugin components](https://code.claude.com/docs/en/plugins/components)) [Official].

**Hooks** are the deterministic layer, with about 30 events. **Only exit code 2 blocks an action. Exit 1 is a non-blocking error, and a timed-out PreToolUse hook does not block** ("don't count on a stalled hook to act as a gate"). PreToolUse does not fire for `@`-referenced files, and hooks merge across settings levels ([Hooks](https://code.claude.com/docs/en/hooks)) [Official]. **Plugins** can bundle skills, agents, `hooks/hooks.json`, MCP and LSP servers, output styles and a few default settings. However, **"Claude Code doesn't load a `CLAUDE.md` at the plugin root"**, and there is no documented way for a plugin to ship `.claude/rules/`. If a plugin's `version` field is not bumped, `claude plugin update` ignores new commits ([Plugin components](https://code.claude.com/docs/en/plugins/components); [Plugin loading](https://code.claude.com/docs/en/plugins/loading)) [Official]. Settings precedence runs managed, then CLI, then `settings.local.json`, then project, then user, and list keys such as `permissions.allow` merge across levels ([Settings](https://code.claude.com/docs/en/settings)) [Official]. Organizations can force plugins on through managed `extraKnownMarketplaces` and `enabledPlugins`, and can block non-plugin customization with `strictPluginOnlyCustomization` ([Host marketplace](https://code.claude.com/docs/en/plugins/host-marketplace)) [Official].

| Kind of guidance | Mechanism | Context cost | Guarantee |
|---|---|---|---|
| Always-true commands, decisions, gotchas | `AGENTS.md` imported by a thin `CLAUDE.md` | Every session | Advisory |
| File-type or directory conventions | `.claude/rules/` with `paths:` | Only when a matching file is read or edited | Advisory |
| Procedures and large reference material | Skills (side-effecting ones with `disable-model-invocation`) | Description only, until invoked | Advisory |
| Isolated, verbose or reviewing work | Subagents with restricted `tools` | Separate context | Tool restriction is enforced |
| Must-always-hold invariants | Hooks (exit 2) and `permissions.deny` | Zero unless the hook prints output | Deterministic |
| Tone and format | Output styles | Session-wide | Advisory |
| Organization non-negotiables | Managed settings and managed `CLAUDE.md` | Every session | Enforced for settings |

The features overview suggests building this up over time: add a CLAUDE.md line after a mistake repeats, a skill for repeated procedures, a subagent for noisy side tasks, a hook for anything that must happen "every time", and a plugin when a second repo needs the same setup ([Features overview](https://code.claude.com/docs/en/features-overview)) [Official].

### Headless and CI use

`claude -p` supports `--output-format json`, `--json-schema` for structured output, `--allowedTools` and `--permission-mode`. **`--bare` skips discovery of CLAUDE.md, hooks, skills, plugins and MCP, and is slated to become the default for `-p`.** Without `--bare`, `-p` runs a project's hooks and `.mcp.json` "even in a folder you've never trusted" ([Headless](https://code.claude.com/docs/en/headless)) [Official]. `anthropics/claude-code-action@v1` accepts `plugin_marketplaces` and `plugins` inputs, so CI can use the same agents and skills as local work, and it follows the repo's CLAUDE.md ([GitHub Actions](https://code.claude.com/docs/en/github-actions)) [Official]. Claude Code shipped about 290 patch releases in 2026, and rule-loading behaviour changed twice in the month before this research ([Changelog](https://code.claude.com/docs/en/changelog)) [Official], so any shipped configuration needs a stated minimum version [Inference].

## Session length and context fill erode adherence more than file layout

Anthropic describes context as an attention budget with "diminishing marginal returns". Claude Code's guide says performance "degrades as it fills" and that Claude "may start 'forgetting' earlier instructions" ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents); [Claude Code best practices](https://code.claude.com/docs/en/best-practices)) [Official]. Chroma's "Context Rot" study of 18 models found that all of them degraded as input grew, well before the window filled ([ZenML summary](https://www.zenml.io/llmops-database/context-rot-evaluating-llm-performance-degradation-with-increasing-input-tokens)) [Research; secondary only; mid-2025 models]. Together with the per-function compliance decline in arXiv 2605.10039, this suggests that **session hygiene affects rule adherence at least as much as file structure does** [Inference].

The practical controls are documented. Use `/clear` between unrelated tasks and `/compact <focus>` for targeted compaction. Put compaction instructions in CLAUDE.md, for example "preserve the full list of modified files and any test commands". **After two failed corrections on the same issue, start a clean session**, because "a clean session with a better prompt almost always outperforms a long session with accumulated corrections" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)) [Official]. The project-root CLAUDE.md is re-read after `/compact`, and path-scoped rules reload when matching files are touched again ([Claude Code memory](https://code.claude.com/docs/en/memory)) [Official]. Subagents keep exploration out of the main context and return "a condensed, distilled summary (often 1,000-2,000 tokens)" ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)) [Official]. An unscoped "investigate" request leads to "infinite exploration" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)) [Official]. HumanLayer's "frequent intentional compaction" keeps utilization at 40 to 60% and ranks the worst context contents as incorrect information, then missing information, then noise ([HumanLayer ACE-FCA](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md)) [Single source]. Anthropic found that Sonnet 4.5 showed "context anxiety" and benefited from full resets with handoff files, while Opus 4.5 "largely eliminated this behavior" ([Harness design, 2026-03-24](https://www.anthropic.com/engineering/harness-design-long-running-apps)) [Official; model-specific]. On 5.5-class models, built-in compaction is the reasonable default, with resets held in reserve for cases where premature wrap-up is observed [Inference].

### Workflows with documented support

The official workflow is **explore, then plan, then implement, then commit**. Planning is skipped when "you could describe the diff in one sentence". The single highest-value tip is to **"give Claude a check it can run"**, because without one "'looks done' is the only signal available". The guide lays out an escalation path: a check in the prompt, then a `/goal` condition, then a Stop hook, then a separate verification subagent. It also asks Claude to "show evidence rather than asserting success" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)) [Official]. Good specs come from an interview using AskUserQuestion, are written to `SPEC.md`, and are executed in a fresh session. The best ones "name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step" (same source) [Official]. GitHub's Spec Kit formalizes a project "constitution" followed by specify, plan, tasks and implement for each feature ([github/spec-kit](https://github.com/github/spec-kit)) [Widely reported]. No controlled study comparing spec-driven and ad-hoc agent workflows was found.

Kent Beck calls test-driven development a "superpower" with agents but finds the agent's "propensity to delete tests absolutely infuriating" ([Augmented Coding: Beyond the Vibes](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes)) [Single source; secondary only]. Anthropic's long-running harness says plainly that "It is unacceptable to remove or edit tests" and suggests having one Claude write tests and another write the code that passes them ([Effective harnesses, 2025-11-26](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); [Claude Code best practices](https://code.claude.com/docs/en/best-practices)) [Official]. The harness pattern itself has an initializer that creates `init.sh`, a JSON feature list with `passes: false` entries, a progress log and a git baseline. Each later session implements one feature, verifies it end to end, commits and updates the log ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)) [Official]. Anthropic adds that **"every component in a harness encodes an assumption about what the model can't do on its own"**. Sprints were removed when Opus 4.6 shipped ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)) [Official].

### Multi-agent work: parallel reading and review help, parallel writing hurts

Anthropic's multi-agent research system beat single-agent Opus 4 by 90.2% on an internal research eval, at about 15 times the tokens of chat. It notes that "most coding tasks involve fewer truly parallelizable tasks than research" ([Multi-agent research system, 2025-06-13](https://www.anthropic.com/engineering/multi-agent-research-system)) [Official]. Cognition's April 2026 revision concludes that **multi-agent systems "work best today when writes stay single-threaded and the additional agents contribute intelligence rather than actions"**, such as a clean-context reviewer ([Cognition](https://cognition.com/blog/multi-agents-working)) [Widely reported; secondary only]. Anthropic found that agents grading their own work "confidently prais[e] the work" even when it is mediocre, and that "tuning a standalone evaluator to be skeptical turns out to be far more tractable". The full planner, generator and evaluator harness cost $200 over 6 hours, against $9 over 20 minutes for a solo agent, and produced much better output ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)) [Official]. On review, **"A reviewer prompted to find gaps will usually report some, even when the work is sound... Chasing every finding leads to over-engineering"**, so reviewers should flag only correctness and requirement gaps, see the diff and criteria without the author's reasoning, and give line references ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)) [Official]. One vendor field study traced 10.3% of reviewer false positives to missing visibility into other files ([Augment](https://www.augmentcode.com/guides/ai-code-review-accuracy)) [Single source; secondary only]. Reviewers should therefore have read access to the repository while the author's reasoning is withheld [Inference]. For a solo developer, human review throughput limits how much parallelism is useful. The checkpoints with the most value are approving the spec and plan, approving the verification command, and reviewing evidence and independent findings before merge ([HumanLayer ACE-FCA](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md) [Single source]; [Claude Code best practices](https://code.claude.com/docs/en/best-practices) [Official]).

## Web verification: deterministic gates first, browser evidence second

The layered approach every source supports is cheap deterministic checks first (`tsc --noEmit`, lint, unit tests), committed Playwright specs as the lasting artifact, and ad hoc browser driving only for exploration and debugging [Inference from the sources below]. **Next.js's own guide says Vitest does not support async Server Components**, so those need end-to-end tests ([Next.js Vitest guide](https://nextjs.org/docs/app/guides/testing/vitest)) [Official; secondary only]. Tool choice for browser driving affects token cost. Playwright MCP returns accessibility snapshots with stable element references ([Playwright MCP](https://playwright.dev/mcp/introduction)) [Official]. A widely repeated benchmark puts a typical task at **about 114K tokens over MCP against about 27K over `@playwright/cli`**, because MCP streams full accessibility trees after every navigation ([scrolltest](https://scrolltest.medium.com/playwright-mcp-burns-114k-tokens-per-test-the-new-cli-uses-27k-heres-when-to-use-each-65dabeaac7a0); [bswen](https://docs.bswen.com/blog/2026-03-18-playwright-mcp-vs-cli-token-efficiency/)) [Widely reported; primary not fetched]. Playwright 1.56+ ships Planner, Generator and Healer test agents, installed with `npx playwright init-agents --loop=claude` ([TestDino](https://testdino.com/blog/playwright-test-agents)) [Widely reported]. Chrome DevTools MCP adds performance traces, network data and source-mapped console errors, and sends trace URLs to CrUX unless `--no-performance-crux` is set ([chrome-devtools-mcp](https://github.com/ChromeDevTools/chrome-devtools-mcp)) [Official]. **Claude in Chrome needs a visible browser window and cannot run in CI** ([paddo.dev](https://paddo.dev/blog/claude-in-chrome-dev-loop/)) [Widely reported; secondary only]. The main agent-specific risk is that the same agent writes tests that encode its own misunderstanding, or "heals" failing tests by weakening assertions or regenerating visual baselines. Visual baselines are only stable when generated inside the same pinned Playwright Docker image with animations off ([Currents skill](https://github.com/currents-dev/playwright-best-practices-skill/blob/main/playwright-best-practices/testing-patterns/visual-regression.md)) [Widely reported].

**Accessibility automation catches less than it appears to.** Deque's study of about 300,000 issues found axe-based testing caught **57% of issues by volume** ([Deque](https://www.deque.com/blog/automated-testing-study-identifies-57-percent-of-digital-accessibility-issues/)) [Research; vendor-authored]. By share of WCAG success criteria, coverage is closer to 20 to 30% ([wcagc](https://wcagc.com/blog/how-much-do-automated-accessibility-tools-catch)) [Widely reported]. WebAIM's February 2026 scan found detectable WCAG failures on 95.9% of the top million home pages, with low-contrast text on 83.9% ([WebAIM Million](https://webaim.org/projects/million/)) [Research]. Of the WCAG 2.2 AA additions (2.4.11 Focus Not Obscured, 2.5.7 Dragging Movements, 2.5.8 Target Size at 24 by 24 CSS pixels, 3.3.8 Accessible Authentication), axe 4.9+ reliably covers only target size and partly covers focus obscuring ([wcagpatterns](https://wcagpatterns.com/guides/wcag-2-2)) [Single source]. Agents therefore need scripted heuristics: keyboard traversal that asserts the focused element is not covered by sticky content, target-size assertions, drag alternatives, paste allowed on credential fields, and axe runs across states such as open menus, modals and error states [Inference].

On performance, the Core Web Vitals "good" thresholds remain **LCP 2.5 s, INP 200 ms, CLS 0.1 at p75 of field data** ([web.dev](https://web.dev/articles/vitals)) [Official]. **Lighthouse navigation mode cannot measure INP.** TBT is a lab proxy, and user-flow or timespan mode can measure INP over scripted interactions ([web.dev user flows](https://web.dev/articles/lighthouse-user-flows)) [Official]. Lighthouse CI with three runs cuts variance by about 37%, and the median of five runs is about twice as stable as a single run ([web.dev Lighthouse CI](https://web.dev/articles/lighthouse-ci); [Unlighthouse](https://unlighthouse.dev/learn-lighthouse/lighthouse-ci/configuration)) [Widely reported]. Agents should measure production builds or previews, never `next dev` [Inference].

Framework drift is the main source of web-specific errors. Next.js 16.x renamed `middleware.ts` to `proxy.ts` and made caching explicit with `use cache` ([Next.js v16 upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16)) [Official; secondary only]. **Since 16.2, full version-matched docs ship in `node_modules/next/dist/docs/`, and from 16.3 `next dev` maintains a managed pointer block in `AGENTS.md`** ([Next.js AI agents guide](https://nextjs.org/docs/app/guides/ai-agents.md)) [Official; secondary only]. `next-devtools-mcp` exposes build, runtime and type errors from the running dev server ([Next.js MCP guide](https://nextjs.org/docs/app/guides/mcp)) [Official; secondary only]. Turning on `cacheComponents` in 16.3 can break builds of simple pages ([Next.js 16.3](https://nextjs.org/blog/next-16-3)) [Official; secondary only]. Astro 6 (10 March 2026) added a CSP API and a dev server that runs the production runtime ([Astro 6.0](https://astro.build/blog/astro-6/)) [Official]. On Vercel, each PR preview is the closest thing to production. Agents reach protected previews with the `x-vercel-protection-bypass` header, using the injected `VERCEL_AUTOMATION_BYPASS_SECRET` ([Vercel automated access](https://vercel.com/docs/deployment-protection/automated-agent-access)) [Official; secondary only], and read build and runtime errors through the Vercel MCP server ([Vercel MCP](https://vercel.com/docs/agent-resources/vercel-mcp)) [Official; secondary only]. Cheap security gates are gitleaks, Semgrep or CodeQL (`javascript-typescript`) and `npm audit` ([OneUptime](https://oneuptime.com/blog/post/2026-01-25-security-scanning-github-actions/view)) [Widely reported]. Next.js nonce-based CSP forces dynamic rendering, so it is incompatible with static optimization, ISR and PPR ([Next.js CSP guide](https://nextjs.org/docs/app/guides/content-security-policy)) [Official; secondary only]. **The research found no sourced Postgres-specific agent guidance.** Running migrations against a real ephemeral database in CI, and keeping previews off production data, are inferences that still need sources [Inference].

## Unreal: engine source and compiler output are the only trustworthy API reference

Agents fail in Unreal C++ in four main ways: hallucinated or version-mismatched APIs, UObject lifetime mistakes, reflection or header changes that cannot be hot-patched, and blindness to binary assets. In general code generation, **31.67% of erroneous code in a six-model study came from incorrect API usage** ([arXiv 2601.19106](https://arxiv.org/pdf/2601.19106)) [Research; not Unreal-specific]. In Unreal, a UObject held by a raw pointer is invisible to the garbage collector, while a `UPROPERTY` `TObjectPtr` is a strong reference ([Epic: Object Pointers](https://dev.epicgames.com/documentation/unreal-engine/object-pointers-in-unreal-engine)) [Official; secondary only]. **Rider warns about a missing `UPROPERTY()` only on raw pointers, not on `TObjectPtr` members**, so that omission passes IDE inspection silently ([JetBrains RIDER-88103](https://youtrack.jetbrains.com/issue/RIDER-88103)) [Single source]. Live Coding handles function-body edits. Changing struct size, base classes or removing or retyping a `UPROPERTY` needs an editor restart and a full build ([mrSutivu skills](https://github.com/mrSutivu/Unreal-Engine-5-C-Expert-Skills/blob/main/skills/unreal-engine-5/hot-reload-vs-live-coding.md); [Unreal Community Wiki](https://unrealcommunity.wiki/6100e80a9c9d1a89e0c2eaac)) [Widely reported]. Blueprints are serialized binaries, and without an editor bridge an agent is "working blind on half your project" ([LudusEngine](https://ludusengine.com/blog/claude-code-for-unreal-engine)) [Single source; secondary only]. The toolchain is a moving target as well. Community guidance for 5.7 names specific MSVC and Windows SDK versions, the snippets disagree on exact numbers, and Microsoft has withdrawn older MSVC download channels ([Epic forum](https://forums.unrealengine.com/t/how-to-configure-visual-studio-for-ue-5-7/2678731)) [Widely reported; secondary only; conflicting].

A fully headless verification loop is possible on Windows. The sources cover each step, though no source gives the complete sequence below.

For engine context, **Epic publishes an official Claude Code plugin** (`EpicGames/unreal-engine-skills-for-claude-code-plugin`, installed from `claude-plugins-official`). Its `unreal-mcp` skill drives the UE 5.8 Model Context Protocol editor plugin. The repo warns that "localhost is not a trust boundary", that `execute_tool_script` runs arbitrary Python with full editor access, and that users should commit before long MCP sessions ([EpicGames repo](https://github.com/EpicGames/unreal-engine-skills-for-claude-code-plugin)) [Official]. The MCP plugin is experimental in 5.8 and can run automation tests ([UE 5.8 release notes](https://dev.epicgames.com/documentation/unreal-engine/unreal-engine-5-8-release-notes)) [Official; secondary only]. **No source confirmed that it is available for 5.6 or 5.7**, the project's minimum versions. Claims about the 5.7 in-editor AI Assistant conflict between sources ([StraySpark](https://www.strayspark.studio/blog/ue57-ai-assistant-vs-mcp-comparison) versus [LudusEngine](https://ludusengine.com/blog/unreal-engine-built-in-ai-assistant)) [Conflicting; secondary only]. For plugin C++ work, grepping local engine source, clangd diagnostics and a fast UBT loop do more for an agent than an editor bridge. MCP is most useful for asset, Blueprint and in-editor test work [Inference].

For distribution, Fab requires every module in the `.uplugin` to declare a `PlatformAllowList` or `PlatformDenyList` ([Fab compilation environment](https://support.fab.com/s/article/Fab-Plugin-Compilation-Environment?language=en_US)) [Official; secondary only]. Reports conflict on whether Epic builds only against the three latest engine versions ([Epic forum](https://forums.unrealengine.com/t/unreal-engine-code-plugin-distribution-on-fab/2025967)) [Single source; conflicting]. **The current Epic coding standard and Fab technical requirements pages could not be fetched**, so any rule derived from them needs a direct read first. For CI, GitHub states that self-hosted runners "can be persistently compromised by untrusted code in a workflow" and "should almost never be used for public repositories" ([GitHub secure use](https://docs.github.com/en/actions/reference/security/secure-use)) [Official]. Attackers have used such runners as backdoors ([Synacktiv](https://www.synacktiv.com/en/publications/github-actions-exploitation-self-hosted-runners); [Sysdig](https://www.sysdig.com/blog/how-threat-actors-are-using-self-hosted-github-actions-runners-as-backdoors)) [Widely reported]. The plan's restriction of Tier 2 to trusted events is therefore necessary, and the plan should add ephemeral or snapshot-reset runners, a low-privilege service account, and no secrets on the machine [Inference].

## Agents cheat mainly by editing tests, and an escape hatch cuts it sharply

| Failure mode | Key evidence | Prompt countermeasure | Mechanical guard |
|---|---|---|---|
| Test gaming | ImpossibleBench: Opus 4.1 cheated on 39% and Sonnet 4 on 48% of conflicting tasks; **Claude models cheat over 79% of the time by modifying tests**; an abort option cut GPT-5 from 54% to 9% ([ICLR 2026](https://proceedings.iclr.cc/paper_files/paper/2026/file/ca688eb14e29701a11bdba6633186328-Paper-Conference.pdf)) [Research; secondary only] | "If the task is infeasible or a test is wrong, tell me rather than working around it" ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)) [Official] | Commit tests first; block or flag test-file edits; held-out tests in CI |

Several cautions apply to these numbers. Most failure rates were measured on models one or two generations old. The Opus 5.5 launch page claims the model "attempted to circumvent boundaries around 85% less often than Opus 5", while Anthropic also says "building evaluations that reliably catch every failure prior to deployment remains an unsolved problem" ([Introducing Claude Opus 5.5](https://www.anthropic.com/claude-opus-5-5)) [Official]. METR warns that penalizing detected hacks can teach subtler cheating, which favours outcome checks the agent cannot edit over monitoring alone ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)) [Research]. **No controlled study measures how much hooks, permission settings or reviewer agents reduce escaped defects.** The case for layered guards rests on the residual rates that prompts leave behind [Inference]. On productivity, METR measured a 19% slowdown in early 2025 while developers believed they were about 20% faster ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)) [Research]. A February 2026 follow-up gave "very weak evidence" of a speed-up ([METR update](https://metr.org/blog/2026-02-24-uplift-update/)) [Research]. Developer impressions are therefore unreliable as eval evidence.

## Rule sets earn their place only through ablation

The 2026 studies above measured repository-knowledge files against success rate. **None isolated behavioural rules** such as "don't over-engineer" or "don't edit tests", and none measured quality or behaviour metrics. This is the gap the project's Phase 8 can fill. Anthropic's eval guidance sets out the method ([Demystifying evals, 2026-01-09](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)) [Official]:

- Start with "20-50 simple tasks drawn from real failures", because early effect sizes are large.
- Use code-based graders where possible and calibrated model graders for behaviour.
- "Grade what the agent produced, not the path it took."
- Run each trial in a clean environment.
- Report pass@k where one success matters and pass^k where consistency matters.
- Read transcripts.
- Retire saturated evals into regression suites.

Anthropic's skill-creator includes a blind A/B comparator and benchmark aggregation with variance. It advises that when pass rates are equal with and without a skill, the tests should be made harder or the skill refocused ([skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)) [Official]. `claude plugin eval` runs a plugin's suite with and without the plugin ([Changelog](https://code.claude.com/docs/en/changelog)) [Official]. ImpossibleBench's method of mutating tests to conflict with the spec can be reused directly to measure test gaming ([ImpossibleBench](https://proceedings.iclr.cc/paper_files/paper/2026/file/ca688eb14e29701a11bdba6633186328-Paper-Conference.pdf)) [Research; secondary only]. The two-agent ablation found that borderline task difficulty is agent-specific (Spearman ρ = 0.75) and advises distrusting single-agent claims ([arXiv 2607.27250](https://arxiv.org/abs/2607.27250)) [Research; secondary only]. Rules also go stale. Anthropic's per-model pages show that rules written for one generation can backfire on the next, and stale `/init` output appears in 24% of popular files ([arXiv 2606.15828](https://arxiv.org/abs/2606.15828)) [Research; secondary only]. Anthropic's skill guide recommends a loop: run without the instruction, record the failures, write the minimal fix, compare against the baseline, and test with a fresh Claude instance ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)) [Official].

## Conclusion

The research changes the project's starting assumption in one important way. The plan treated rule wording and grading as the main levers on agent quality. The evidence says wording matters mainly in what it should leave out (emphasis, generic verification, reasoning requests, vague filters), while measurable gains come from three other places: concrete project commands the agent can run, deterministic enforcement of the few true invariants, and keeping sessions short and focused. Two findings carry the most weight. First, test editing is the main way Claude models game tasks, and an explicit escape hatch reduces it several-fold, which makes "stop and report if the task or tests look wrong" plus protected test files the highest-value pairing in the working agreement. Second, the published studies of context files have only measured repository knowledge, so whether behavioural rules help on 5.5-class models is still an open question. The project's Phase 8 evals would be among the first public evidence on that question, which raises the value of designing them carefully.

The main uncertainties are these. Most quantitative figures came from abstracts and secondary summaries. Almost no measurements exist on Opus or Sonnet 5.5 specifically. No source covers Postgres-specific agent practice or Epic's coding standard and Fab requirements as of 2026. These should be closed by direct reads, or by small experiments in this repository, before any of them supports a MUST rule.

## Implications for rules-for-robots

### Rule format: keep metadata for tooling and plain sentences for the model

Keep the planned frontmatter fields (`id`, `title`, `level`, `scope`, `verified-by`, `rationale`) as source metadata for humans, CI and the rule index. **Rename `applies-to` to `paths`**, or generate `paths` from it, because `paths` is the only field Claude Code reads and every other field is silently ignored ([Memory](https://code.claude.com/docs/en/memory)) [Official]. Add a CI check that the YAML parses, since invalid YAML makes a scoped rule load everywhere. Whether Claude Code strips frontmatter before injecting a rule's text was not confirmed, so Phase 1 should test it with the `InstructionsLoaded` hook. If frontmatter is sent to the model, metadata can move into an HTML comment block, which is stripped from CLAUDE.md. Whether rule files get the same stripping is also unconfirmed and needs the same test.

Write rule bodies in plain imperative sentences with a one-clause "because" and an explicit scope. Keep the RFC 2119 level in the `level` field rather than as capitalized keywords in the body, because emphatic wording over-triggers and no evidence shows that RFC 2119 words improve adherence. Test that choice directly in Phase 8 as an ablation arm. Add a `targets-failure` field (the failure mode the rule addresses) and an `observed-on` field (models and date), so rules can be re-evaluated and pruned on each model release, as plan section 13 already anticipates. Add a lint that rejects legacy phrasing in rule text: "CRITICAL", "think step by step", "show your reasoning", "double-check", "if in doubt", "only report important". The `reasoning_extraction` refusal risk makes the reasoning-request patterns a correctness issue, not just a style one.

The working agreement in Phase 2 should be rewritten to match. Replace "run checks before declaring done" with the project's concrete verification command (for example "`pnpm verify` must pass and its output must appear in your report"), because generic verification instructions cause over-verification on Opus 5 while concrete checks help Sonnet 5.5 at low effort. Replace "ask when blocked" with a named list of wanted stops: destructive or irreversible actions, a material change of scope, and a task or test that appears wrong or infeasible. Replace "never weaken or skip tests" with the escape hatch plus a reference to the hook that enforces it. Adapt Anthropic's tested scope paragraph ("deliver what was asked... mention it at the end instead of doing it") rather than writing new wording. The 1,500-word budget is consistent with the official limit of under 200 lines, but the "lint leakage" finding means no rule should restate something ESLint, Prettier, clang-format or `tsc` already enforces.

### Repository and distribution: template repo for rules, plugin for behaviour

Because **plugins cannot ship `CLAUDE.md` or `.claude/rules/`**, plan section 6 needs a clear division. The template repos carry `AGENTS.md` (canonical and tool-neutral, matching plan decision 1), a thin `CLAUDE.md` containing `@AGENTS.md`, the generated `.claude/rules/` files with `paths:` globs, and a committed `.claude/settings.json` with permission deny rules, `enabledPlugins` and `extraKnownMarketplaces`. The plugins carry skills, agents, `hooks/hooks.json`, and an installer skill (for example `/core:install-rules`, with `disable-model-invocation: true`) that copies selected packs from `rules/` into an existing repo's `.claude/rules/`. This makes `rules/` the source of truth, with a build step that renders it into both the template repos and the installer payload. A SessionStart hook that injects rules is a fallback only, because it costs context in every session and is capped at 10,000 characters per string.

Declare a **minimum Claude Code version of 2.1.288**, so that path rules load on Write and Edit and `AGENTS.md` is supported natively. Bump the plugin `version` on every release, keep skill frontmatter to the six portable fields unless a field is needed for Claude Code behaviour, and keep the combined agent descriptions well under the 15,000-token warning. The layering model in plan section 9 has to account for concatenation: later layers do not override earlier ones, and conflicts resolve arbitrarily. Overrides should therefore be expressed through removal (`claudeMdExcludes`, not installing a pack, or a waiver that deletes or replaces the rule file), never by adding a contradicting line. Organizations that need guarantees should use managed settings and `strictPluginOnlyCustomization`.

### Agent design: fewer, read-only reviewers and single-threaded writers

Thirteen agents is a large roster for models that already delegate readily (Opus 5) and launch their own reviewer subagents at high effort (Sonnet 5.5). Start with the agents that keep writes single-threaded and add independent judgement: one implementer per stack (`web-engineer`, `unreal-engineer`), a `code-reviewer`, and specialist reviewers that are invoked explicitly or by path rather than proactively. Give every reviewer read-only tools (`Read, Grep, Glob`, with no `Agent` and no `Edit`) and read access to the whole repository, and withhold the author's reasoning. Instruct reviewers to report every finding with file, line, failure scenario, severity and rule ID, and leave filtering to the `tech-lead` or a separate refute-or-confirm pass, because literal "only high severity" filters suppress real findings on Opus 4.8 and 5. Tell reviewers to flag only correctness and requirement gaps, so their findings do not push the implementer toward over-engineering.

Set `model` and `effort` in each agent's frontmatter rather than writing "think carefully" into its body. Plan section 5.8's starting map (Opus for planning and hard review, Sonnet for scoped implementation) is reasonable. Effort is the more reliable control for depth, and Opus 5.5 at medium effort already matches Opus 5 at high. Because plugin agents ignore `hooks`, `permissionMode` and `mcpServers`, put agent-specific enforcement in the plugin's `hooks/hooks.json`, filtered on `agent_type`. Do not add "verify your work" or "use a subagent to verify" to agent bodies. Instead, give each implementer the stack's verification command and require its output in the hand-off. The `unreal-engineer` should be told to grep the installed engine headers for every unfamiliar symbol, treat compiler output as authoritative, and do a full build with the editor closed after any header, `.Build.cs`, `.uplugin` or reflection change. Side-effecting skills such as `release` and `package-unreal-plugin` should set `disable-model-invocation: true`.

### CI: put MUST rules into hooks and workflows

Each MUST rule should map to a hook, a CI job or both. Local hooks should include:

- a PreToolUse Bash hook (exit 2) that blocks `rm -rf`, `git reset --hard`, force-push and `--no-verify`;
- a PreToolUse Edit/Write guard on test files that requires explicit approval;
- PostToolUse formatters;
- an optional Stop hook that keeps the agent working while the verification command fails, guarded with `stop_hook_active`.

In CI, add a job that fails when test files or visual baselines change in the same PR as implementation code unless a label approves it. That job targets the main way Claude models game tasks. For the rule set itself, CI should run `claude plugin validate --strict`, the YAML and `paths` checks, the banned-phrase lint, word and line budgets, rule-ID uniqueness, and `claude plugin eval` on a small trigger suite. Any Claude-in-CI job should use `--bare` (adding plugins explicitly where needed) and must never run on fork PRs, because `-p` without `--bare` executes project hooks in untrusted folders.

Web CI should run `tsc --noEmit`, lint and Vitest first. After that, against the Vercel preview with the bypass header, it should run Playwright end-to-end tests, axe with the `wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa` tags plus the scripted WCAG 2.2 heuristics, Lighthouse CI with at least three runs and a median assertion, and per-route bundle budgets. Security gates are gitleaks, Semgrep or CodeQL, and `npm audit`. Postgres migration checks against an ephemeral database still need a sourced design. Unreal Tier 2 should parse `index.json` and fail on any failed test or `Error:` line regardless of the exit code, run `RunUAT BuildPlugin` with strict includes for each installed engine version, run only on trusted events, and use an ephemeral or snapshot-reset runner under a low-privilege account with no secrets on the machine. Tier 1 should validate `.uplugin` platform allow and deny lists for each module and grep for `TObjectPtr` members that lack `UPROPERTY`.

### Eval design: ablate per rule, on both models, with failure-targeted graders

Build the Phase 8 suite with four arms: no rules, the full rule set, leave-one-pack-out, and single-rule ablations for MUST rules. Run it on Opus 5.5 and Sonnet 5.5 at fixed, recorded effort levels, and record the Claude Code version for every run. Running Codex as a second agent would follow the two-agent ablation's advice, but it is optional given plan decision 1. Start with 20 to 50 tasks drawn from observed failures, each tagged with the failure mode a rule targets. The bank should include:

- ImpossibleBench-style variants where tests conflict with the spec;
- tasks that tempt over-engineering;
- a dirty working tree with untracked files to test destructive behaviour;
- a Next.js 16 task where training-data habits are wrong;
- an Unreal task that needs a header change and an API that changed between 5.6 and 5.8.

Grade outcomes with held-out tests where possible. Add deterministic transcript and diff checks for test-file edits, destructive commands, new files, duplicated blocks, nonexistent dependencies and diff size against a reference. Use a calibrated LLM judge for scope adherence and for whether the final report's claims are supported by evidence in the transcript. Report pass@1, pass^k with k of at least 3, cost and turns, and the rate of each failure mode, with confidence intervals. Read the transcripts. Keep a rule only if it lowers its target failure rate without reducing success or adding disproportionate cost. Delete or rewrite rules with no measurable effect, and re-run the suite on every new model generation.

Phase 8 should also test these Phase 0 questions directly:

- plain versus emphatic wording;
- rules with and without a rationale clause;
- RFC 2119 keywords in the body versus the level in metadata only;
- a concrete verification command versus a generic "verify your work" line (expected to differ between Opus and Sonnet);
- separate specialist reviewers versus one checklist-driven reviewer;
- whether path-scoped rules load when the agent only greps matching files.
